# מפות אופליין — OsmAnd &amp; מובידוס

אתר GitHub Pages להורדה חופשית וללא הגבלה של מפות אופליין עבור OsmAnd ונתוני מובידוס.

## מבנה הפרויקט

```
index.html                     דף הבית
privacy-policy.html            מדיניות פרטיות
js/app.js                      לוגיקת הצד-לקוח (חיפוש, הורדות, מודאל סטטוס)
data/osmand-data.json          מסד כל קבצי ה-obf (נכתב אוטומטית)
data/mapsTags.json             תגיות עברית/אנגלית לכל קובץ (נכתב אוטומטית)
data/moovitdos-link.json       קישור לקובץ הנתונים העדכני של מובידוס (נכתב אוטומטית)
data/update-status.json        מצב העדכון האחרון של שני המקורות (נכתב אוטומטית)
update-scripts/data-update.py  מריץ כל 3 דקות — מעדכן OsmAnd + מובידוס
update-scripts/tag-generator.py מריץ יומי (06:00) — יוצר תגיות באמצעות Gemini
.github/workflows/              הרצה אוטומטית יומית + הרצה ידנית (workflow_dispatch)
```

## הפעלה ראשונית

1. **דחפו (push) את התוכן הזה למאגר GitHub חדש**, ובGitHub Pages settings הגדירו
   פריסה מ-branch `main`, תיקיית root.
2. **הוסיפו secret בשם `GEMINI_API_KEY`** תחת Settings → Secrets and variables →
   Actions, עם מפתח ה-API של Gemini שלכם.
3. ודאו ש-Settings → Actions → General → Workflow permissions מוגדר ל-
   **"Read and write permissions"**, כדי שה-workflows יוכלו לדחוף (push) עדכונים בחזרה למאגר.
4. אפשר להריץ את שני ה-workflows באופן ידני (tab **Actions** → בחרו workflow →
   **Run workflow**) כדי לבדוק שהכול עובד לפני שממתינים ליום הראשון של ריצה אוטומטית.

## הערות טכניות

- ה-cron של GitHub Actions תמיד לפי UTC ואינו זז עם שעון קיץ/חורף ישראלי — ראו
  הערה בכל קובץ workflow לגבי הפער המשוער.
- `data-update.py` מוריד ומחלץ רק קבצי `*.obf.zip` מרשימת OsmAnd; כל סוג קובץ אחר
  ברשימה מתעלם ממנו לחלוטין.
- **קבצי ה-obf לא נשמרים ב-git**: git/GitHub חוסמים לצמיתות כל קובץ בודד שנדחף
  (push) מעל 100MB, וחלק גדול מקבצי OsmAnd (ארצות שלמות) גדולים מזה בהרבה. הפתרון:
  כל קובץ obf מועלה כ-Asset על GitHub Release ייעודי בתוך המאגר הזה (בדיוק כמו
  שמובידוס עצמו מנהל את קובץ הנתונים שלו) — Assets תומכים בקבצים עד כ-2GB, ואינם
  משפיעים בכלל על גודל ה-push של git, כי רק קבצי ה-JSON הקטנים ב-`data/` נדחפים
  בפועל. `data/osmand-data.json` שומר כתובת URL קבועה לכל קובץ.
  - קובץ בודד מעל **1.9GB** (מרווח בטיחות מתחת למגבלת ה-Asset של GitHub) נרשם
    לצמיתות ב-`osmand-oversized-files` ולא ינסה להיכנס אוטומטית — במציאות אף קובץ
    מפה אמיתי לא צפוי להתקרב לגודל הזה.
  - `data-update.py` רץ כל 3 דקות (concurrency group מבטיח שלא ירוצו שתי ריצות
    במקביל). כל ריצה מוגבלת ל-2GB הורדה/העלאה (`MAX_RUN_DOWNLOAD_BUDGET_BYTES`) —
    זה כבר לא קשור למגבלת git, רק שומר שכל ריצה תהיה קצרה וסבירה ברשת. כל מה שלא
    נכנס לריצה הנוכחית נרשם ב-`osmand-pending-files` וייכנס אוטומטית בריצה הבאה.
  - **תקציב זמן פנימי**: ה-job עצמו נחסם לצמיתות אחרי `timeout-minutes: 10`, וזה
    מבטל את כל השלבים כולל "Commit and push" — כלומר כל התקדמות שלא נשמרה עד אז
    אובדת, וגם קבצים שכבר הועלו ל-Release ידרשו העלאה חוזרת מיותרת. כדי למנוע
    את זה, הסקריפט עוקב אחרי זמן הריצה שלו ועוצר את עצמו ביוזמתו אחרי 8 דקות
    (`MAX_RUN_SECONDS`) — מרווח בטוח מתחת למגבלת ה-job — ומסיים ריצה רגילה כדי
    שהשלב של "Commit and push" תמיד ירוץ. בנוסף, `osmand-data.json` נשמר בפועל
    אחרי כל קובץ בודד שהועלה בהצלחה (לא רק בסוף הריצה), כך שגם תקלה חיצונית בלתי
    צפויה (כמו קריסת ה-runner עצמו) לא תאבד קבצים שכבר הועלו.
    כתוצאה מכך, בעומס גדול, ריצות עשויות לקחת עד כ-8 דקות במקום 3, וזה תקין —
    ה-concurrency group ידאג שהריצה הבאה תמתין בתור.
  - כל עוד יש `osmand-pending-files`, השדה `osmand-in-progress` הוא `true` והאתר
    מציג "עדכון הנתונים מתבצע כעת" (רק אם אין שגיאה). כל עוד `osmand-in-progress`
    הוא `true`, `tag-generator.py` לא עושה כלום ומסתיים מיידית, כדי לא לתייג קבצים
    שהמידע עליהם עדיין לא סופי.
  - השימוש הוא ב-`secrets.GITHUB_TOKEN` המובנה (לא צריך ליצור טוקן בעצמכם) — ודאו
    רק ש-Workflow permissions מוגדר ל-"Read and write permissions" כמתואר למעלה,
    וזה מספיק גם ליצירת/עדכון ה-Release וגם לדחיפת השינויים ב-`data/`.
  - **הערה על מכסות**: ל-GitHub Releases (בשונה מ-Git LFS) אין מכסת bandwidth/storage
    חינמית מפורסמת, אך עדיין כפוף למדיניות השימוש הסביר של GitHub. אם המאגר יצטבר
    לכמויות עצומות של מפות, שווה לעקוב שאין חסימות בלתי צפויות.
- מובידוס: מכיוון שדף ה-GitHub Pages של מובידוס טוען את קישור ההורדה באמצעות JS,
  והמאגר המקורי כנראה פרטי, הסקריפט מחלץ מספר גרסה מתוך הדף עצמו ובונה את כתובת
  ה-URL הידועה (`.../releases/download/v{X}/moovidos_data_v{X}.zip`). קובץ הנתונים
  של מובידוס עצמו **אינו** מועתק למאגר הזה — רק הכתובת נשמרת, וההורדה מתבצעת ישירות
  מול GitHub.
- מפתח ה-Gemini API אף פעם לא נחשף בצד הלקוח — הוא משמש רק בתוך ה-workflow של
  `tag-generator.py`, בצד השרת.
